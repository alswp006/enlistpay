# Architecture Review
Generated: 2026-09-06T21:47:08.340Z
Score: 64/100

## Summary
The codebase has a clear domain/storage/component layering with good inline documentation and consistent UI wrapper patterns (haptics, TDS pre-built components, safe SDK guards), but it suffers from real duplication (repeated haptic helpers, chip-casting bridges, table derivations, sort logic) and a risky dual-type-system: `lib/contract.ts` and `domain/types.ts` independently define same-named types (`RouteState`, `PayTable`, `VacationRecord`) with different shapes. There's also a dead/legacy storage abstraction (`lib/storage.ts`) coexisting with the real one (`storage/core.ts`), and inconsistent import-path conventions (relative vs `@/` alias) across pages. No circular dependencies were found, and domain calculation logic (date/pay/rank/vacation) is cleanly separated.

## Issues
### Critical
- [naming] `RouteState`, `PayTable`, and `VacationRecord` are each declared twice with completely different shapes: once in `src/domain/types.ts` (re-exported via `src/lib/types.ts`) and once in `src/lib/contract.ts`. Because both are commonly imported side-by-side (e.g. `storage/vacation.ts`, `domain/vacation.ts`, `domain/pay.ts`), an accidental unaliased import of the wrong one type-checks fine but silently uses the wrong shape. — Files: src/domain/types.ts, src/lib/contract.ts, src/storage/vacation.ts, src/domain/vacation.ts, src/domain/pay.ts / Fix: Rename the contract-side types (e.g. `ContractVacationRecord`, `ContractPayTable`, `NavRouteState`) at declaration site instead of relying on every consumer to alias on import, or merge the two type systems into one source of truth.
